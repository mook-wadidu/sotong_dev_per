# 파일럿 운영 — 확정된 결정 (2026-08-07)

이 문서는 **소통 레포 쪽에서 알아야 하는 파일럿 운영 규칙**만 모은다. 코드에는 안
드러나지만 코드를 고칠 때 전제가 되는 것들이다.

전체 개시 체크리스트(도메인·메일·법무 등 대표 몫)는 MAKEDOL 레포의
`additional documents/OWNER-CHECKLIST.md` 에 있다. 배포·시크릿 규칙은 이 레포의
`CLAUDE.md`.

---

## 1. 손님이 인테이크에 도달하는 경로 — 링크 발송

**예약 확정 후 운영자가 손님에게 인테이크 링크를 수동으로 보낸다.**

원래는 MAKEDOL 확정 메일에 링크를 자동으로 싣는 설계(외부 참조 연동)였는데 파일럿에서
뺐다. 20명이면 `consultation_id` 연결은 어드민 수동 20클릭이고, 자동화가 아끼는 게
정확히 그 20번이라 만들 이유가 없었다.

**그런데 그걸 빼면서 손님의 도달 경로가 같이 사라졌다.** 수동 연결은 「붙이는」 얘기지
「도달하는」 얘기가 아니다. 그래서 명시한다.

### 왜 QR 이 아니라 링크인가 — 파일럿이 재는 것이 갈린다

| | 손님이 채우는 시점 | 검증되는 것 |
|---|---|---|
| **링크 발송** | **방한 전** — 디자이너가 사전 정보를 받는다 | **사전 예약 인프라** ← 우리 오퍼 |
| 도착 후 QR | 현장 | 현장 상담 도구 |

오퍼가 「방한 전 사전 신청」이고 A0 의 **「예약확정 → 인테이크 진입률」** 지표가 링크
발송을 전제한다. QR 만 쓰면 그 숫자가 무의미해진다.

**QR 은 매장 비치 폴백**으로 남긴다 — 링크를 잃은 손님용.

### 링크는 손님별이 아니다

`src/lib/entry.ts` 의 진입 토큰은 두 종류뿐이다:

```
d:{designerId}.v{version}   디자이너별
s:{salonSlug}.v{version}    살롱 공용
```

**손님을 가르지 않는다.** 전 손님이 같은 링크를 쓴다. 손님별 토큰을 만들려면 새 종류가
필요한 신규 개발이라 파일럿 밖이다.

공유 때문에 생기던 두 문제는 2026-08-07 에 둘 다 막았다:

- **앞사람 드래프트가 다음 손님에게 넘어가던 것** — `intake-stepper.tsx` 의 자동저장 키가
  `entryToken` 단위라 매장 태블릿에서 전 손님이 공유했다. 알레르기까지 실려 있었다.
  → 민감·식별 필드는 저장에서 제외(`DRAFT_STRIP`) · 복원은 명시적 선택(`resume` 화면) ·
  30분 만료
- **매장 전체가 한 상한 버킷을 공유하던 것** — `intake:{entryToken}` 8/분이라 토큰만 알면
  원격에서 분당 8번 찔러 그 매장의 접수를 통째로 막을 수 있었다.
  → 주 상한을 **IP**(`intake-ip:` 20/분)로 옮기고 토큰은 60/분 천장으로

**링크를 뽑는 곳**: 오너 콘솔 QR 탭(`src/components/salon-console/qr-tab.tsx`).
지금은 어드민에 발송 버튼이 없으므로 거기서 복사해 수동 발송한다.

## 2. 파일럿 동안 소통 어드민을 열지 않는다

파일럿 동선에서 **소통 어드민이 아니면 못 하는 일이 없다**(조사 완료):

| 동선 | 어디서 |
|---|---|
| 예약 확정 · `consultation_id` 연결 | MAKEDOL 어드민 |
| 인테이크 링크 발송 | 오너 콘솔 QR 탭에서 복사 (§1) |
| 상담 확인 | 오너 콘솔 — `salon-console.tsx` 가 `consultations` 를 받는다 |
| 리포트 | 오너 콘솔 `owner-reports-tab` |
| 디자이너 초대 | 오너 콘솔 `designers-tab` → `createSalonInvite(ownerToken)` |
| 손님 시술 이력 | 오너 콘솔 `customer-history` |

어드민 전용은 **전 살롱 교차 뷰**(`admin-analytics`·`admin-designers`·`admin-reports`)·
`admin-dataset`·`admin-announcements`·`onboarding`(살롱 생성)인데, **살롱이 1곳이면 교차
뷰는 오너 콘솔과 같은 데이터**고 살롱 생성은 끝났다.

⚠️ 예외 하나 — **고객센터 메모**(`inquiry-notes` → `support_notes`)는 어드민에만 있다.
손님 컴플레인을 남기고 싶을 때만 연다.

**→ 파일럿 동안 어드민을 몇 번 열었는지 센다.** 0번이면 파일럿 후 제거 대상, 몇 번이면
그 기능만 옮긴다.

### 지금 MAKEDOL 로 통합하지 않는 이유

어드민을 MAKEDOL 하나로 합치자는 방향 자체는 맞다. `admin-auth.ts`·`admin-session.ts`·
`SOTONG_ADMIN_TOKEN` 이 통째로 사라지고, 어드민이 둘이라 생기는 순서 사고
(2026-08-07 의 `admin@` 삭제 = MAKEDOL 잠김)의 절반이 없어진다.

**그런데 옮기면 안 되는 것이 있다** — 살롱 생성 · `entry_key_version` 회전 · 스태프 초대 ·
export 는 **소통 자체의 운영 도구**다. MAKEDOL 로 옮기면:

- 「소통은 MAKEDOL 없이 돈다」는 경계 근거가 깨진다
- 🔴 **역방향 결합**이 생긴다. 스키마 소유자는 소통인데 MAKEDOL 이 `salons`·`staff`·
  `entry_key_version` 에 **쓰기** 시작하면 **소통 마이그레이션이 MAKEDOL 을 깨뜨린다.**
  `grep bookings src/` 를 0건으로 지켜온 것의 정확히 반대 방향이다

파일럿 동안은 SQL 직접으로 충분하다(살롱 1곳, 회전 없음, 초대 몇 번).
**지금 통합하지 않는 이유는 하나 — 새 기능 개발이고 파일럿을 하루도 앞당기지 않는다.**

## 3. `role='admin'` 은 대표 계정 둘뿐이다 — 파일럿 불변식

`getAdminUser()` 가 이메일 문자열이 아니라 **`profiles.role`** 을 본다(2026-08-07 변경).
그 행은 대시보드/직접 SQL 로만 만들 수 있고, `provisionAccount` 호출부 6곳이 전부
`designer`/`owner` 만 넘기므로 **가입 경로는 `admin` 에 구조적으로 도달할 수 없다.**

⚠️ **`profiles.role` 은 이제 접근 제어다.** 지금까지는 아무도 갱신하지 않는 필드였지만
(디자이너가 오너가 돼도 `designer` 로 남는다) 이제는 아니다.
**role 은 명시적 UPDATE 로만 바꾼다 — upsert 금지**(`upsertProfile` 은 `onConflict:"id"`
라 role 을 덮어쓴다).

매장 계정을 만든 **뒤에** 한 번 더 확인한다:

```sql
select id, email, role from public.profiles where role in ('admin','operator');
-- 기대: 대표 계정 둘뿐 (bill@wadidu.com, mook@wadidu.com)
```

오너 콘솔에서 디자이너를 등록하면 `role='designer'`, 원장이 계정을 가지면 `role='owner'`
가 생긴다. 지금은 안전하다 — `OPERATOR_ROLES={'admin','operator'}` 라 MAKEDOL 에 안 닿고
소통 어드민도 `'admin'` 만 본다. **하지만 그 안전이 「우연히 아무도 admin/operator 를 안
만들었다」에 기대고 있으므로** 계정이 늘어난 뒤 위 쿼리를 다시 돌린다.

## 4. 손님 계정 — MAKEDOL 에 생겼다 (2026-08-07)

MAKEDOL 에 **이메일 인증 + 비밀번호** 가입이 붙었다. `app_users` 테이블은
`0037_app_users.sql` 로 **이 레포의 마이그레이션 체인**에 들어 있지만,
⚠️ **소통 코드는 그 테이블을 읽지도 쓰지도 않는다.** 체인만 공유하고 결합은 만들지
않는다 — 체인을 둘로 가르면 「레포만으로 프로덕션 스키마가 재현된다」(468컬럼 일치)가
깨지기 때문에 같은 체인에 둔 것뿐이다.

같이 바뀐 것: **Supabase 프로젝트의 공개 가입(`disable_signup`)을 닫았다.**
계정 생성은 전부 서버(Admin API)를 지난다. 소통의 `provisionAccount`·
`acceptSalonInvite`·`signUpDesigner` 는 전부 Admin API 라 **영향 없다**
(`auth.signUp` 호출 0건 확인). 공개 엔드포인트로 직접 가입하려던 경로만 닫혔다.

### 소통 쪽 `customers` 병합은 아직이다

MAKEDOL 계정과 소통 `customers`(device+살롱 단위, 이메일 컬럼 없음)는 아직 안 붙는다.
붙일 때의 규칙은 이미 정해뒀다:



승계(기존 device 행을 버리고 새로 시작)는 손님이 로그인하면 **지금까지 쌓인 자기 이력을
잃는다.** 계정을 만들 이유 자체가 없어진다. 그래서 **병합**이다.

1. 같은 살롱의 device 행들을 `auth_user_id` 아래로 묶고, **가장 최근 `created_at` 행을
   정본**으로
2. 나머지 행은 **지우지 않고 `merged_into` 포인터만** — 잘못 병합했을 때 되돌릴 수 있어야
   한다
3. 🔴 **알레르기·화학이력은 어느 행에서도 안 가져온다.** 로그인이 프리필 금지(안전결함
   A4 — 공유기기에서 타인의 값이 실려 실제 알레르기가 은폐됨)를 **우회하는 경로가 되면 안
   된다**
4. 병합은 **같은 살롱 안에서만**

`app_users` 위치는 아직 미정 — 착수 시점에 정한다.

## 5. 인용하지 말 것 (2026-08-07 에 고쳐진 것)

계획 문서에 사실로 적혀 있었지만 **지금은 아닌 것들**이다. 고쳐진 사실을 근거로 다음
계획을 짜는 게 이 프로젝트에서 반복된 실수라 따로 적는다.

| 예전 기술 | 지금 |
|---|---|
| `hasPii`/`redactConsultationPii` 가 갈라져 자유텍스트만 있는 상담은 파기 대상에서 빠진다 | 단일 분류 맵(`retention.ts` `INTAKE_PII`)으로 통합 |
| `intake.name`·`allergy` 가 PII 파기를 통과한다 | 파기됨 |
| `sessionStorage` 드래프트가 손님 간 공유된다 | §1 참조 — 막음 |
| `enforceRate` 의 fail-open 이 이중·무음이다 | 드라이버가 던지고, 통과 결정은 한 곳, `logIssue` 로 남음 |
| `rate_limits` 청소 코드가 0건이다(주석은 청소를 약속) | `0036` 이 함수 안에서 2% 확률로 청소. 쌓여 있던 218행 정리됨 |
| anon/authenticated 에 테이블 GRANT 가 남아 있다 | `0035` 로 462 → 0. `alter default privileges` 까지 |
| 어드민 권한의 출처가 이메일 허용목록이다 | `profiles.role` (§3) |

**주석을 근거로 쓰지 않는다.** `0003` 의 청소 약속과 `0001` 의 「anon 에 미부여」 주석이
둘 다 거짓이었다.
